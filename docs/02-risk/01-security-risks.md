# 2-1 リスク対策：情報漏えい・モデル改ざん・故障停止

評価：発生しやすさ（高/中/低）× 影響（大/中/小）。対策は「導入時」と「点検時」に分けて書く。

## A. 情報漏えい

| # | リスク | 起こりやすさ／影響 | 導入時の対策 | 点検時の対策 |
|---|---|---|---|---|
| A-1 | AIサーバーの管理画面・API（例：Ollama の 11434番ポート）が社内LAN全体や外部に公開される | 中／大 | 推論エンジンは `127.0.0.1` のみで待ち受け。利用者は管理画面（認証あり）経由でのみ使う。ルーターでポート開放しない | 月次で待ち受けポート一覧を確認（チェックリスト S-02） |
| A-2 | 推論エンジンの脆弱性（［調査］2026年に Ollama で深刻な脆弱性 "Bleeding Llama"（CVE-2026-7482、v0.17.1で修正）等が報告。約30万台が無認証で公開と報道） | 中／大 | バージョン固定＋検証機で確認してから更新。外部非公開を徹底 | 月次で脆弱性情報を確認、重大なものは臨時更新（S-05） |
| A-3 | 機密業務でクラウドAIを使ってしまう | 高／大 | 機密区分（L1〜L3）とUI上のモデル分離。クラウドモデルは許可グループのみ表示。社内ルール1枚を配布 | 月次でクラウドAI利用ログを抽出し、L3らしき入力がないか抜き取り確認 |
| A-4 | 社内文書検索で、本来見られない部署の文書が見えてしまう | 中／中 | 文書の登録単位を部署・権限ごとに分ける（ナレッジ単位の権限設定） | 四半期でアカウントと権限の棚卸（S-01） |
| A-5 | 遠隔点検経路からの侵入（当社が踏み台になる） | 低／大（全顧客に波及） | [06-remote-maintenance.md](../03-design/06-remote-maintenance.md) の対策（外向き接続のみ、MFA、顧客ごとの通信分離、顧客側で停止可能） | 当社の作業端末も月次で点検。アクセス記録を顧客に開示 |
| A-6 | 当社が顧客データを持ち出す・紛失する | 低／大 | 顧客データは当社端末に保存しない（点検は遠隔で中身を見ずに行う）。作業端末はディスク暗号化 | 年1回、当社の自己監査を顧客に報告 |
| A-7 | 退職者アカウントが残る | 中／中 | 管理者に退職時削除の手順を渡す | 四半期の棚卸 |
| A-8 | 文書に仕込まれた指示でAIが誤動作（プロンプトインジェクション） | 低〜中／中 | 外部から受け取った文書はRAG登録前に確認。AIに外部送信やファイル操作の権限を与えない（ツール実行機能はオフ） | 精度点検時に異常回答を確認 |

## B. モデルの改ざん（非公式モデルの危険）

［調査］2025年2月、Hugging Face 上で悪意あるコード入りモデル（PyTorch/pickle形式、読み込むとリバースシェル）が見つかり、スキャナーをすり抜けて8か月以上放置されていた（"nullifAI"）。悪意あるモデルの大半は pickle 形式とされる。

| # | リスク | 対策 |
|---|---|---|
| B-1 | 読み込むだけでコードが実行されるモデルファイル（pickle 形式 `.bin` `.pt` `.pkl`） | **使うのは `safetensors` か `GGUF` 形式のみ**。pickle形式は使用禁止 |
| B-2 | 名前を似せた偽モデル（タイポスクワッティング）、非公式の量子化版に細工 | **取得元を限定**：①開発元の公式アカウント、②推論エンジン公式のライブラリ、③事前に審査した配布者のみ（ホワイトリスト）。それ以外は使わない |
| B-3 | 取得後のファイル差し替え | 取得時に SHA-256 ハッシュを記録し「モデル台帳」に記入。月次点検でハッシュを再照合（S-04） |
| B-4 | モデル自体に仕込まれた偏り・裏口（特定の言葉で誤回答） | 完全な検出は不可能。→ 実績のある開発元のモデルに限る／精度点検の固定質問セットで挙動変化を監視／重要判断はAI任せにしない運用を契約に明記 |
| B-5 | ライセンス違反モデルの使用 | モデル台帳に「ライセンス・商用可否・確認日」の欄を設ける |

**仮決め：** モデル取得元のホワイトリストは「開発元公式＋推論エンジン公式ライブラリ」の2種に絞り、第三者の量子化版は原則使わない。
- 理由：一人で配布者の信用を継続審査するのは難しい。
- 別案：コミュニティで定評のある量子化配布者を数名だけ追加で許可（性能・選択肢は増えるが、審査責任が当社に乗る）。

## C. 故障・停止

| # | リスク | 対策 |
|---|---|---|
| C-1 | 機材故障（電源・SSD・GPU） | メーカーのオンサイト保守／翌営業日交換保守を付けられる機種を標準に。保守契約期間は3〜5年 |
| C-2 | 停電・瞬停 | UPS（無停電電源装置）を標準装備。停電時は自動シャットダウン |
| C-3 | 夏場の熱暴走（工場・現場事務所） | 設置場所を事前確認（直射日光・粉塵・高温を避ける）。温度を監視し閾値で通知 |
| C-4 | ディスク満杯・ログ肥大 | 監視とログ自動削除 |
| C-5 | 更新による不具合 | 自社検証機で先に更新 → 問題なければ顧客へ。更新前に設定バックアップ。ロールバック手順を用意 |
| C-6 | 設定・索引データの消失 | 日次で顧客社内のNASまたは外付けディスクへバックアップ（社外には出さない）。月次で復元テスト（四半期でも可） |
| C-7 | 当社（一人）が動けない | 代替要員と再委託契約。手順書・認証情報の封緘保管（顧客の金庫等）。[02-contract.md](02-contract.md) に明記 |
| C-8 | ソフトの開発停止・ライセンス変更 | 比較表で代替候補を常に1つ持つ（[02-inference-engine.md](../03-design/02-inference-engine.md)）。データは標準形式で保持し乗り換え可能に |
